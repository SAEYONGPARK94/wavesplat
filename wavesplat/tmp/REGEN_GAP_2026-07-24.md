# REGEN_GAP — closing the 2026-07-23 dataset-regeneration coverage gap

**Date**: 2026-07-24. **Scope**: the `fixedT` episodes the 2026-07-23 regeneration left on the
sub-Nyquist raycast mesh, plus the first mesh-adequacy census of `BF4_20comp`, `BF6` and `BF7`.

**Authority chain**: `tmp/REGEN_SPEC_fable_2026-07-23.md` §0 explicitly deferred the `fixedT`
family — *"if the broader PhD CRB/envelope work depends on `fixedT` files at the coarse mesh,
that is a materially identical problem to this one and should get its own, later regen pass
reusing this same spec's mesh choice — flagged, not actioned here."* This is that pass.

**Procedure**: unchanged from `tmp/regen_fixedT_a7.py` (which is itself
`tmp/regen_run_finemesh.py`'s procedure, REGEN_SPEC §5). Nothing was invented. Mesh
**200×167** (dx 1.2060 m, dy 1.2048 m) is the *only* intervention; seed, `n_pts` cap,
duration, dt, depth, raydrop model and wave direction are all read back from the shipped
file and reproduced exactly, so the comparison stays paired.

### Crash tolerance / resumability

* Every episode is generated into `<out>/_staging/` and only `os.replace`d into place after
  an openability check — a kill mid-`save_episode` cannot leave a truncated file in the
  output dir.
* Resume skips only files that pass `is_complete()` (opens as HDF5 **and** has non-empty
  `frames/lidar_points`, `frames/gt_wave_field`, `config/wave_components`). A truncated file
  is deleted and redone rather than silently skipped forever.
* The manifest is rewritten (atomically, via `.tmp` + `os.replace`) after **every** episode.
* Per-episode `try/except`: one failure records `status: fail` + traceback and the batch
  continues.
* An unreadable *shipped source* records `status: source_corrupt` and is skipped, not raised
  (`data_corrupt_slope_files.md` — none of the 85 `fixedT` sources turned out to be corrupt,
  see §3).

## 2. The 8000-observation cap

REGEN_SPEC's fixedT companion (`scripts/d3_e3_regen_finemesh.py` L26-29) notes: *"The stored
fixedT episodes cap at 8000 returns/frame, not the config's 50. Regenerating at the config
default would have changed the observation count as well as the mesh — two interventions,
one experiment."*

**Verified, not assumed**: all 85 shipped `*_fixedT*.h5` carry `frames/lidar_points` of shape
`(301, 8000, 3)` and `raydrop_model.attrs['cap'] == 8000`. The driver reads that cap per
file (`raydrop_model/cap`, falling back to `n_pts`) rather than hardcoding it, and the
verification pass asserts the regenerated point-array width equals the shipped width. So the
cap is *preserved from the source file*, not re-imposed by assumption — which also makes the
same driver correct for the `n_pts=50` BF6/BF7 extras (§4).

So the fixedT family was, in a weaker sense, already covered — at the thinner-margin mesh
(1.3% below the 1.3595 m ADEQUATE-for-all threshold, vs 11.3% for 200×167), in a scratch
directory, without the `mesh_verdict` provenance attr (those files predate it; they carry
`mesh_dx`/`mesh_adequate` but not the string verdict). This pass supersedes it with the
same 200×167 mesh everything else since 2026-07-23 uses. `scripts/d3_e7_wavefield_figs.py`
still reads `tmp/finemesh_clean/` directly and should be repointed if those figures are
regenerated.

## 6. What was deliberately *not* done

* **No generator fixes.** REGEN_SPEC's G2 (angular-noise range-scaling bug), G4, G7, G8 and
  the raydrop-model defects (b)/(c) are all held fixed, exactly as in the 2026-07-23 pass,
  so any post-regen delta is attributable to the mesh alone.
* **No `peak_locked` companion for fixedT.** The 1-comp fixedT episodes stay on the
  spectral flank, matching the shipped files and the `data_finemesh_fixedT_2026-07-23/`
  set generated on 2026-07-23.
* **`episode_BF4_30comp_seed42_uniform.h5`** (the other stray REGEN_SPEC §0 named) is a
  `uniform` episode, not `fixedT`, and was left alone — it is outside this task's brief and
  outside the `default.yaml` grid.
* **No downstream re-run.** Nothing in `results/` or `paper/` was recomputed here; the
  consumer table in §4 lists what *could* now be re-run on adequate data. In particular
  `scripts/d3_a2_dir180_eval.py`'s A-2 directional-invariance result (30 head-sea episodes,
  28 of which were sub-Nyquist until now) is the largest single re-derivation this unblocks.

### The 4 "bit-close, not exact" extras

`BF6_15comp`, `BF6_30comp`, `BF7_15comp`, `BF7_30comp` differ from their shipped counterparts
by **exactly one ULP** (`1.1e-16`, single amplitude cell — verified: `omega/kx/ky/phi/Q` are
all bit-identical, only one `A` value moves in the last bit) — a floating-point reassociation
in `jonswap_components`' amplitude normalization, three orders of magnitude inside
REGEN_SPEC §6.3's `rtol=1e-10` bar. **Not a regression.** The 56 fixedT files and the other 6
extras (all lower component counts) reproduce bit-for-bit. This ULP wobble appears only at
15/30 components, consistent with a longer normalization sum. Every episode still shares the
same wavenumbers/frequencies/phases, so the pairing is intact.

### Runtime / resource notes

* ~5–8 min/episode (GPU raycast, 200×167). Ran two disjoint-shard workers
  (`--shard 0/2` / `1/2`, private staging + manifest) to share the card with the already-
  running paper-table re-run without racing it; the whole gap closed in ~3.7 h of wall clock.
* An earlier single-worker attempt was `nice -n 10`; under a heavy concurrent `pytest` +
  ETKF-tuning load it was CPU-starved (the per-frame `evaluate_field`/`interpolate_normals`
  is CPU-bound, not GPU-bound — REGEN_SPEC's own timing finding), so it was relaunched at
  normal priority. Two workers at normal nice coexisted fine with the GPU jobs (card stayed
  ~15–40% util, <6 GB of 16 GB).
